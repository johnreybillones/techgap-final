## 1. Output contract

Create the following under `data/pre_model/<release_id>/`; write UTF-8 JSONL with one object per line, sorted by stable ID, and a final newline. `prepare` builds in a temporary directory, validates, then atomically renames it into place. After agents write decision files, `finalize` writes each derived output to a temporary file and atomically replaces that output; it never rewrites agent input or source files. If an existing release ID has different input/rule hashes, fail instead of overwriting it.

| File | One row per | Minimum fields and purpose |
| --- | --- | --- |
| `documents.jsonl` | selected job or syllabus JSON | `document_id`, `source_type`, source paths/hashes, original and normalized metadata, `full_text`, `text_transform_version`, selected/alternate versions for jobs, status/warnings for syllabi, applicability/eligibility/relevance states, `split_group_id`. Every source remains traceable even when its text is unusable. |
| `passages.jsonl` | distinct prepared passage | `passage_id`, `document_id`, `source_type`, `field`, `field_item_id`, `text`, `document_start`, `document_end`, source references, `quality_flags`, `source_aliases`, `split_group_id`. `document_start:end` reproduces the passage from that document's derived full text. Every alias has its own `document_id`, field, offsets and source hash. |
| `annotation_queue.jsonl` | passage/chunk needing AI decisions | Stable ID, full text and source context, source hash, permitted labels, processing instructions and split group. Reuse checked annotations for identical hash/rule/prompt versions on rerun. |
| `job_decisions.jsonl`, `span_drafts.jsonl`, `ai_checks.jsonl` | AI-agent inputs to `finalize` | One job decision and first-pass span decision per corresponding queue ID; one independent check per job decision and span draft. Each carries source hash, agent/model/configuration/prompt version. Never silently overwrite prior agent output. |
| `annotations.jsonl` | AI decision on queue item | Exact spans, contextual labels, source/provenance, agent/model/prompt version, checker decision and unresolved reasons. This is silver data, not gold truth. |
| `issues.jsonl` | invalid or unresolved source/annotation item | Source ID/path, stage, reason code, evidence and retry eligibility. Include invalid ID/URL pairs, missing text, uncertain completeness, malformed JSON, mismatched spans and AI disagreements. |
| `gliner2_train.jsonl`, `gliner2_val.jsonl`, `gliner2_test.jsonl` | checked training example | Native `{"input": ..., "output": {"entities": ...}}` format with explicit spans. Keep model-specific files separate from provenance-rich `annotations.jsonl`. |
| `manifest.json` | release | Input file hashes, cutoff, rules/prompts/model versions, output hashes, count table, split method/seed, exclusions and warnings. No accuracy claim. |

Use full lowercase SHA-256 hex digests for stable derived IDs: `document_id` is the established JobStreet key for jobs and `syllabus:` plus SHA-256 of the syllabus JSON's repository-relative path for syllabi; `passage_id` hashes canonical JSON of `{document_id, field, field_item_id, document_start, document_end, text_transform_version}`; a chunk ID hashes `{passage_id, chunk_start, chunk_end, text_transform_version}`. Canonical JSON means UTF-8 `json.dumps(..., sort_keys=True, separators=(',', ':'), ensure_ascii=False)`; hash original files as raw bytes. Preserve aliases under the primary passage ID; choose the lexicographically smallest `(document_id, field, field_item_id, document_start)` as primary after sorting. Never use mutable row order as identity. Offset units are Python Unicode character indices with exclusive end. An offset is valid only when `text[start:end]` exactly equals the saved mention. Keep empty, null, and missing source fields distinguishable in metadata. `manifest.json` hashes every other generated file but not itself.

## 2. Task A — read and reconcile saved job evidence

- [ ] Link each observation to its version by `(release root, version_id)` and to its posting by `posting_key`. - [ ] Preserve all versions and their raw pointers. - [ ] Preserve original title, company, URL, location, work type/arrangement, salary if present, actor/run/dataset/query/page references and unknown versus null. ## 4. Task C — passages, quality, and cross-source deduplication

- [ ] Preserve one derived full text per selected job/syllabus source. A job passage is one nonempty paragraph or list item after HTML cleanup; headings are context metadata for following passages, not standalone training examples. Keep its source start/end. A syllabus passage is one description, CLO, TLO or `additional_text` item. Do not split a short passage further. For a passage over **384 whitespace words**, find token spans with `re.finditer(r'\S+', text)` and make windows of tokens `[0:384]`, `[320:704]` and so on, ending at the last token; each adjacent window overlaps by 64 words. Use the first/last token character offsets to slice the original passage, so every chunk reproduces its exact source substring. Record chunk-local and document offsets. At export, require each labeled span **and its containing AND/OR clause** to fit in one chunk; if none does, exclude that span with reason rather than cut its qualifier. Never truncate at a model `max_len` and assume the remainder was processed. GLiNER2's documented long-context pattern uses overlapping chunks and remapped spans. [GLiNER2 long-context guide](https://github.com/fastino-ai/GLiNER2/blob/main/tutorial/12-long_context.md).
- [ ] Remove only transport/layout noise: HTML tags, duplicate whitespace, empty list items and repeated extraction headers/footers that are demonstrably outside competency sentences. Preserve original case and terms such as `C++`, `C#`, `.NET`, `R`, `SQL`, `and/or`, negation and version numbers. Do not stem, lowercase model text, replace aliases, translate in place, or turn statements into keyword bags. Normalized comparison keys may lowercase/collapse whitespace **without replacing** model input text.
- [ ] Within one selected job, collapse exact repeated passages for model examples while retaining all positions. Across different JobStreet IDs, do **not** merge postings or analysis counts. For leakage grouping only, link exact same cleaned description; also link a near-duplicate candidate when normalized employer and title match and `difflib.SequenceMatcher` description ratio is at least 0.90. Record the comparison rule and candidate evidence; if employer/title is missing, require exact description identity. Treat connected candidates as one split group. This is conservative leakage control, not a claim that IDs are the same vacancy. Repeated boilerplate alone is insufficient to link whole jobs.
- [ ] For syllabus examples, exact repeated passage text shared by course versions or lecture/lab sources is one labeled example with all aliases. An exact comparison key is Unicode NFC plus collapsed whitespace, preserving case and punctuation; use the same rule for job-passage exact duplicates. No exact comparison key may occur in more than one split. Link affected course groups before splitting. Keep unique phrases and every course-level evidence pointer.
- [ ] Add `language=english|non_english|uncertain` to the AI passage decision, checked in the second pass. Keep original-language text/source links. Export only checked `english` passages to the initial GLiNER2 splits; leave `non_english` and `uncertain` in the annotated corpus. A later translation must be a separate derived artifact with translator/model/prompt and source linkage, and cannot claim source-exact spans. Do not add a heuristic language package for this corpus.

**Focused check:** `Python or R` stays one contextual clause; `C++` stays intact; chunk offsets reproduce text; two cross-ID near duplicates remain two documents but share `split_group_id`; shared lecture/lab text appears once in exported examples.

## 5. Task D — source-backed AI decisions before training

Use Codex AI agents operating on local files for semantic decisions; do not add an API integration or paid labeling service. Deterministic parsing, identity, offsets, hashes and validation stay in the script. Save the exact prompt text and agent/model/configuration version in the release. `prepare` writes a sorted `annotation_queue.jsonl` with `kind=job|span`, source/path/hash, exact input text and context, completeness flags, and output ID. Feed contiguous batches of at most 10 queue rows and at most 12,000 total input characters to a first agent (**actual practice 2026-10-30:** Claude subagents, batches of 100 passages from a seeded sample of at most 5 passages per document, Haiku low-effort first pass and a different Sonnet medium-effort checker; job decisions by Sonnet first pass and Sonnet checker; only passages of jobs whose checked decision is relevant are sampled; `scripts/carry_labels.py` copies hash-matching labels into a rebuilt release); one oversized row is its own batch. Append one JSONL decision per queue row. A different agent checks the same batches against the original queue rows and first-pass decisions, including every complete-negative. Append one `ai_checks.jsonl` row per first-pass row. Validate each batch immediately; retry malformed output once with the validation error, then mark that item unresolved. Resume from IDs already present with the same source/rule/prompt hashes; never send an item twice merely because a run was interrupted. Missing or conflicting decisions remain unresolved and excluded from supervised exports. No human approval queue or one-time human sample is required. Do not describe these labels as independent gold.

### D1. Job-level decision record

For each selected job, read the original title plus complete available duties/requirements and write one row to `job_decisions.jsonl`. Required keys: `document_id`, `source_hash`, `relevance` (`relevant|irrelevant|unresolved`), `relevance_basis` (`title|description|both|conflict|insufficient`), `tracks` (zero or more of `bscs_is`, `bscs_game`, `bsit_network`, `bsit_web`), `cohort` (`employment|internship|unresolved`), `ph_eligibility` (`yes|no|unresolved`), `curated_role_id` (always null until the list exists), `evidence` (source field/passage ID, exact start/end/text), `reason`, `agent`, `model`, `configuration`, and `prompt_version`. A source field can be `title` for an obvious title-based link; its offsets apply to the original title. Description evidence offsets apply to the cited prepared passage. Record the ID of the original observation/version as well.

Obvious technical titles may establish broad track: game-development work → BSCS Game Development; AI/ML/data-science work → BSCS Intelligent Systems; NOC/network/system-administration work → BSIT Network Technology; web/mobile-development work → BSIT Web Development. Multiple supported tracks are allowed. For generic, unfamiliar or conflicting titles, use actual duties. Keep relevant general computing postings with an empty track array when no specific track is supported. Use no search-query-derived label. Exclude clearly nontechnical work from technical extraction; unresolved relevance stays visible. Do not force a curated role: its list has not been supplied, so `curated_role_id` remains null. An employment/internship or Philippine eligibility uncertainty remains unresolved and separate from relevance. Keep title and evidence for every decision.

Job-decision prompt: “Read this saved posting's original title, description and source metadata. Decide whether the work is technical computing work, which of the four academic tracks the actual work supports, whether it is an employment or internship/OJT vacancy, and whether the location explicitly permits Philippine applicants. Use the title directly when it clearly names a broad technical role; use duties/requirements when the title is generic or conflicts. Keep general computing relevant without inventing a track. Return only the specified JSON and cite exact title/description substrings with offsets. Query, actor, ESCO, seniority and an unsupplied curated role list cannot supply labels. Mark any unsupported decision unresolved.”

### D2. Passage annotation record and fixed labeling instruction

For each unique job or syllabus passage, show the agent: source type, exact prepared text, immediately preceding heading, adjacent sentence when needed, original source field, completeness/warnings, and the definitions below. Write one JSON row to `span_drafts.jsonl` with `passage_id`, `source_type` (`job|syllabus`), `text_sha256`, `language` (`english|non_english|uncertain`), `spans` (list of `start`, exclusive `end`, `text`, `type`, `clause_start`, exclusive `clause_end`, `modality`), `passage_complete` (boolean), `technical_content` (`present|absent|unclear`), `agent`, `model`, `configuration`, and `prompt_version=technical-spans-v1`. For each span, `clause_start:clause_end` must reproduce the complete source clause containing it, including explicit `and`/`or`, negation and qualifiers; `modality` is `required|preferred|allowed_alternative|unclear` for jobs and `not_applicable` for syllabi. When a clause has two modes, split it at the smallest complete subclauses. This metadata remains in `annotations.jsonl`; only `text/start/end/type` go into GLiNER2 entities.

- `technical_task`: an explicit computing/data/game/network/security/etc. action or ability, including its meaningful object and qualifiers. `technical_knowledge`: an explicit technical concept/domain the person must know or the course teaches. `tool_technology`: a named language, framework, platform, protocol or tool. A sentence may have multiple exact spans, including a nested tool span; offsets select the intended occurrence.
- Select the shortest span that still preserves the capability's scope; keep exact source characters and offsets. Never label salary, degree, years of experience, generic soft skill, benefit, company description, offered training, title alone, or implied technology. A syllabus phrase such as “understand networking” supports only that broad knowledge, not Cisco configuration. Do not infer capability from course name.
- For jobs, keep whether a requirement is required, preferred, an allowed alternative, or unclear **outside** the three entity types. Record complete clause offsets so later grouping can see explicit AND/OR wording. For syllabi, modality is `not_applicable`. If text is truncated or ambiguous, mark `passage_complete=false`/`technical_content=unclear`; extract supported positive spans only. Empty `spans` plus `technical_content=absent` is permitted **only** after the full passage has been checked and is complete. Absence in a partial/missing passage is unresolved, never negative.
- Agent prompt: “Read only the supplied source text and metadata. Return the specified JSON. Quote exact substrings with zero-based, exclusive-end character offsets. Label only explicit technical task, knowledge and tool/technology spans. For each span cite the complete clause offsets and mark its modality. Mark language English only when the competency prose is English; mark mixed/uncertain prose uncertain. Preserve negation and AND/OR scope in the clause; mark uncertainty instead of guessing. Do not use title, search query, CSV, ESCO, or outside knowledge to fill missing text. For a syllabus, do not turn a broad outcome into a specific skill. For a job, distinguish required, preferred and allowed alternatives. If no technical content exists, say absent only when the entire passage is complete.”
- Checker prompt: “Independently read the same source and proposed JSON. Verify every offset and type, source support, modality, AND/OR links, completeness and claimed negative. For jobs also verify relevance, track, cohort and Philippine eligibility against cited title/description evidence. Output `accepted`, `corrected` with a full replacement JSON, or `unresolved` with reason. Do not use the first agent's confidence as evidence.
