# TechGap planned data flow

**Status:** Agreed planning contract, updated 2026-10-31 (international pool added 10-27; refresh section 7 added 10-30; unresolved-score rule, component links, syllabus upload, entry point and result releases added 10-31). This describes the intended data processing and result data; it does not claim that the pipeline has been implemented or validated. It records the decisions reverified in the current discussion. Where older plans conflict, use this contract for the revised design. Keep the older documents as history until their separate revisions are agreed.

**Boundary:** Job acquisition, query tuning, duplicate avoidance, cost and collection targets belong to the collection plan. Backend storage/APIs and frontend layout/interactions may have separate implementation documents later. This file owns the rules that turn saved jobs and syllabus evidence into student and faculty results. Changing an output's meaning requires updating this contract even if its screen or API changes elsewhere.

## 1. Inputs and populations

| Input | Use and limit |
| --- | --- |
| Saved JobStreet postings | Preserve the original title, description, source ID, URL, collection/publication dates, query, and available raw fields. Reuse previously saved IDs when collection or processing is revised. A query identifies candidates; its results are not automatically relevant or members of its originating track. |
| Syllabus JSON in `data/syllabi/` | Use course code, track, description, learning outcomes and available learning-plan text as academic evidence. Include applicable courses even when extraction status is `needs_review`; carry source and completeness warnings. Do not fill missing competency text from a title, CSV, or outside reference. Updated year/semester metadata will be used when supplied. |
| Curated career-role list | Defines the career names students may select and compare. The four academic tracks define track scope; ESCO occupations and search-query labels do not define track or student-facing career labels. |
| Verified learning resources | Used only to link a confirmed gap to a real, suitable learning destination. An absent resource does not erase the gap. |
| CHED CMO 25 reference | Fixed, hand-written file with section citations: program outcomes, 146-unit minimum, six common courses, required knowledge areas per program. Each course is mapped once to a knowledge area. An agent prepares the mapping, with provenance per §6, in the refresh that first sees the course. If the agent cannot map a course, its knowledge area is `unmapped` (never a guess) and the course is not marked CHED-mandated. Used to label suggestions and flag mandated topics. It does not enter any score or count. |

The four supported tracks are **BSCS Intelligent Systems, BSCS Game Development, BSIT Network Technology, and BSIT Web Development**. Relevant common/core computing work and coursework can contribute to the applicable tracks; General Education and informal learning do not create academic coverage.

Include relevant employment postings at **all seniority levels**. Keep actual internship/OJT vacancies in a separate cohort so their counts and results are not mixed with employment. Seniority may be retained as descriptive context, but it neither excludes a relevant job nor changes its technical coverage score. Philippine jobs and remote jobs open to Philippine applicants form the **local pool**. Malaysia, Singapore and Indonesia jobs form a separate **international pool** (decided 2026-10-27). Each pool keeps its own counts and results, like the employment/internship cohorts; the two are never mixed in one demand count or score. A pool with no releasable data has no result set; the application shows "no data yet" for it. The collection period is recent first, with a maximum lookback of twelve months; actual coverage depends on the postings obtained.

## 2. Processing sequence

1. **Preserve and deduplicate.** Keep raw observations and versions; identify distinct postings for analysis. Report returned rows, distinct postings, relevant postings, and assessable postings separately. Never use an older model decision as a gold label.
2. **Decide relevance and links.** Use a clear technical title to link a posting to one or more of the four tracks or a curated career role. For a generic, unfamiliar or conflicting title, inspect the actual duties and requirements. Keep relevant general computing postings even if no specific track or curated role can be supported; they can inform overall computing demand, but not a fabricated track/role profile. Retain the employer title and reason for each link. Do not infer relevance solely from the search query or force an unmatched title into a different career name.
3. **Extract job requirements.** Find source-backed technical capabilities in stated duties and required qualifications. Keep the exact passage, posting ID and whether it is required, preferred, an allowed alternative, or unclear. Preserve task/tool qualifiers and explicit AND/OR wording. Salary, years of experience, education, benefits, soft skills and offered training remain available as context but do not count as technical skills.
4. **Prepare academic evidence.** Read applicable syllabus descriptions, outcomes and learning-plan statements with their course code, track, source field and extraction status. A short syllabus phrase is evidence only for what it actually says. Course title or broad topic alone does not prove a specific job capability. Flag missing or uncertain course evidence instead of dropping the course.
5. **Match the same capability.** Retrieve possible syllabus passages by exact terms/aliases and semantic search, then decide whether those passages support the *same* task, knowledge or tool requirement at the stated scope. Similarity is a search aid, not proof of coverage. For a multi-part requirement, record which parts are supported; preserve allowed alternatives. Use simple parsing first, and compare any proposed extraction or matching model with reproducible automated source and consistency checks before using it. Treat comparisons against AI-generated labels as agreement measures, not independently verified accuracy.
6. **Calculate and publish results.** Derive demand, coverage, gaps, career comparisons, recommendations and roadmaps from the linked evidence. Every result keeps its cohort, track/role, observation window, distinct-posting counts, syllabus version, rule version, and source references. A new model or rule can rerun on saved postings without another paid collection.

An extraction failure leaves a relevant raw posting available for repair but out of demand and coverage calculations that require its missing technical text. It must not count as a posting with zero demand or zero coverage.

## 3. Calculation rules

- A **requirement group** is one independently assessable required capability. Repeated wording in one posting counts once. Explicit alternatives form one OR group; jointly required components form an AND group. Preferred and unclear requirements appear separately and do not inflate the required-skill score.
- A group is **covered** only when the selected syllabus evidence supports every required component, or at least one allowed OR alternative. A group is **partial** when an explicit multi-part requirement has supported and unsupported components. A confirmed unsupported group is **missing**. Insufficient job or syllabus evidence is **unresolved**, not missing. Partial groups receive no full-coverage credit in the strict score.
- **Status for a chosen set of courses S** (decided 2026-10-31). A component is `supported` if some course in S supports it; otherwise `unresolved` if some course in S is unresolved for it; otherwise `not_established`. For an alternative (an AND of components) let s, u and m be its counts of supported, unresolved and not-established components: it is **covered** when m = 0 and u = 0; **partial** when s ≥ 1 and m ≥ 1; **missing** when s = 0 and u = 0; otherwise **unresolved**. A group (an OR of alternatives) is covered if any alternative is covered, else unresolved if any is unresolved, else partial if any is partial, else missing. A group flagged `requirement_unresolved` at release time (insufficient job evidence) is unresolved for every S. Only `supported` and `unresolved` links are stored; a missing link means `not_established`.
- For a posting with a complete set of assessable required groups: `posting coverage = covered groups / distinct required groups`. No assessable required groups means **no score**, not 0% or 100%. With unresolved groups or an incomplete requirement set, qualify or withhold the score rather than silently treating unknowns as misses. Decided 2026-10-31:
  - A posting's requirement set is **complete** when its text is usable, extraction ran on all its passages without failure, and at least one required group was found. No human check is needed.
  - Complete set and every group resolved: the posting is **scored** and enters the role or track mean.
  - Complete set and at least one unresolved group: the posting is **qualified**. It is shown with a lower and an upper bound and does not enter the mean: `lower = covered groups / distinct required groups` and `upper = (covered + unresolved groups) / distinct required groups`. Partial groups get no credit in either bound; with no unresolved group both bounds equal the strict score. The counts behind the bounds are shown beside them.
  - Incomplete set: the score is withheld; the posting is **not scored** and does not enter the mean.
  - Every mean is shown with "N scored / N qualified / N not scored".
- A role or track alignment figure is the **unweighted mean of the coverage of scored postings**, with one contribution per posting; qualified and not-scored postings are excluded and listed beside it (qualified ones with their bounds). With no scored posting there is no figure. Always show how many relevant postings were scored, qualified and not scored. The same rule applies to faculty and student calculations; the syllabus evidence set differs.
- **Observed demand** for a requirement is `n / N`: `n` distinct assessable postings in the selected population that state it, over `N` postings whose technical requirements can be assessed. State the cohort, role/track and time window. Count a requirement once per posting; do not present query-limited sample percentages as population-wide market rates.
- Order confirmed gaps by observed distinct-posting demand. Equal demand ties. Low observed demand is descriptive only; one snapshot cannot establish a decline, obsolescence or a reason to remove a course. No untested weighting, TOPSIS rank, or trend line is needed for the first reliable result.

## 4. Faculty result data

Faculty results compare **all applicable courses in a track** with observed job requirements. They must expose the underlying jobs, course passages, counts and unresolved evidence. Public display of a job (decided 2026-10-31, while source-access consent is unrecorded): title, company, source URL and the short extracted requirement phrase; the job description passage is not republished. Course syllabus passages are shown in full. The following data supports the proposed views; chart type and layout belong to the frontend.

| Output | Data the pipeline can produce |
| --- | --- |
| Industry skill demand ranking | Required technical capabilities ordered by observed `n/N`, with posting counts and cohort/window. |
| Curriculum–skill map | Course-by-capability evidence links with covered, partial, missing or unresolved status; no strength claim based solely on a short phrase. |
| Demand versus curriculum coverage | Each capability's observed demand beside its supported curriculum coverage/status, with denominators and limits. |
| Coverage distribution | Counts or proportions of covered, partial, missing and unresolved requirement groups for a chosen track or curated career role. |
| Career-family comparison | Requirement frequencies and coverage across curated roles that have assessable postings; there is no minimum count, counts are always shown and sparse roles stay visibly sparse. |
| Competency category distribution | Observed requirements grouped into explainable technical categories, with category rules and counts. |
| Course-level relevance evidence | The observed job capabilities a course supports, partly supports, or does not establish, with source passages. Do not invent a course “relevance percentage.” |
| Targeted syllabus-change suggestions | For a confirmed gap: **add** (capability missing) or **extend** (capability partial, naming the unsupported parts), targeting the related course when its current subject provides a defensible link, otherwise a curriculum area. Each carries job evidence, observed demand n/N, the course passage, the CMO knowledge area, and the note that institutional constraints are not in the data. Never a removal. Faculty decides whether to adopt it. |
| Review list | Capabilities supported by at least one applicable course, sorted by observed `n/N` from lowest, descriptive only (§3). There is no cutoff: no threshold is defined, so the reader decides what is low, and `n = 0` means "not observed in this sample", not "not demanded". Marked CHED-mandated when the course's knowledge area is required by CMO 25. |

**Requirement-group links.** For every requirement group a release stores its structure (one or more alternatives, each an AND of components) and, per component, the course codes with syllabus passage reference and status that support it. Support is judged per syllabus passage against one component, so a component is supported when any single course's passage supports it; passages from different courses are not combined for one component. A component's support never depends on which other courses are selected, so the application can derive a student's or faculty's status for any set of courses from the stored links without running a model.

The proposed **skill demand trend** view is deferred. A single query-limited collection snapshot cannot establish how demand changed over time. Salary, hiring outcomes and curriculum effects are likewise not inferred from these records. No hypothetical curriculum simulation is part of this flow.

## 5. Student result data

The system receives a track and the **final set of completed course IDs**. For a regular student, the application may auto-select courses before the chosen year level and semester once reliable placement metadata is supplied. An irregular student may change the completed-course selection freely. This selection behavior is an application concern; the pipeline scores only the completed IDs. Future courses may be shown as possible later coverage but never count toward the current score. A component is **possible later** when the completed set does not support it and some applicable, not-completed course supports it; a group is possible later when its status over the completed set plus all applicable not-completed courses (§3) is covered.

| Output | Data the pipeline can produce |
| --- | --- |
| Ranked career recommendations | Curated career roles ranked by current completed-course coverage of their observed required capabilities. Roles are ordered by combined alignment (§3), highest first. Equal figures share a rank and are displayed in role-name order. There is no minimum number of scored postings: every role with at least one scored posting is ranked and its counts are always shown. Roles with no numeric score follow the ranked roles, labeled "no score" in name order, and stay selectable. Show the competencies driving the ranking, scored, qualified and total posting counts, ties, and evidence limits. This is an academic match, not a measure of personal mastery, hiring probability or eligibility by seniority. |
| Career details | Observed required skills and their covered, partial, missing or unresolved status for the student's completed courses; source job counts and relevant syllabus evidence. Preferred requirements remain separately labeled. |
| Selected career analysis | The chosen role's posting-level and combined alignment, reasons for each status, supporting completed courses, gaps, and future-course possibilities shown separately. A role with no assessable postings remains selectable but has **no numeric alignment score**. |
| Career-specific roadmap | Gaps ordered by observed demand: missing groups, and partial groups with their unsupported components named (for example SQL, from "SQL and Python"), ordered together. Unresolved groups are listed separately as "not confirmed". The roadmap is ordered by observed demand, not by prerequisites. Verified learning resources are attached where available. Show supported alternatives; do not invent a universal prerequisite order or a resource for every gap. |

Employment and internship evidence are identified separately throughout the student results. Raw employer titles without a defensible mapping are never silently displayed as a different curated career.

## 6. Reliability and document ownership

No human-labeled sample or per-posting human approval is required. AI agents may prepare source-backed labels for job relevance/track links, requirement extraction and syllabus support decisions. Record the generating agent/model and configuration, exact source passages, label provenance and any disagreement or unresolved state. Compare simple rules and candidate models on the same source-grouped cases; automatically check span reproduction, schema and identity integrity, logical consistency and source support, then inspect disagreements and recurring errors through a separate automated pass before rerunning saved inputs. AI-generated labels and agent agreement may guide development and training, but they are not independent gold labels. Report agreement and check outcomes as such; do not claim verified precision, recall, accuracy or ranking reliability without independent reference evidence. Keep versioned decisions, incomplete counts and error examples so results can be audited. A small pilot may expose a defect; it cannot establish population-wide accuracy.

Model evaluation outputs (agreement metrics against these AI labels, confidence intervals, training curves) are a separate output class. They describe model quality, never enter a score, count or recommendation, and are defined in the model-pipeline plan.

Suggestion text is a deterministic template filled from saved fields. An optional one-sentence AI rationale is generated once per release, may cite only posting and course IDs supplied to it, is stored with model, configuration and release, and falls back to the template alone if a check fails. It never affects a score or count.

The next collection effort should be a **small cost-capped yield test**, using previously saved IDs to measure genuinely new distinct relevant postings before larger targets. Query and duplicate improvements belong to a separate JobStreet collection discussion; this data-flow contract does not authorize a paid campaign.

The collection document owns acquisition rules. This document owns data meanings and formulas. Future backend and frontend documents should reference these outputs rather than copy their definitions. Open inputs include the updated syllabus placement fields, the curated role list, verified learning resources, and independently measured model quality. Until supplied or checked, dependent results remain qualified rather than filled by assumptions.

## 7. Refresh and model updates

Added 2026-10-30. This section records how results are kept current after new job data or syllabi arrive. It does not change any output's meaning in sections 1–6.

**Decided by the user:**
- Job postings are re-collected **yearly** ([collection plan](JOBSTREET_COLLECTION.md) §8). Syllabi may be **updated by user upload**.
- After new data arrives, results should refresh **with no person involved**.
- New postings are judged for relevance and track by a **small trained classifier**, not an AI agent per posting, because per-posting agent calls cost more. It is trained on the agent-labeled job decisions from the pre-model release. Those labels are silver data, so the classifier is compared with them only by agreement, never by verified accuracy.
- AI labels only: there is no human-labeled test set, so model changes are compared by agent agreement and automated checks.

**Proposed, not yet approved:**
- Run new postings through the current frozen extractor and classifier. This needs no annotation, because annotation only builds training data.
- On each refresh, have an agent label a small random sample of new passages and compare it with the model, and count tool names the training data never contained. This is a drift signal, not accuracy.
- Retrain only when that signal says so, and at most once per semester. A calendar interval of several years is too slow for how fast technical vocabulary changes. Retraining relabels the new data and builds a new release ID with the existing scripts.
- No MLOps platform. A scripted refresh plus versioned release folders is enough at this data size; each manifest already records the model revision. What counts as drift is a threshold for the user to set.

**Open or unverified:**
- **Syllabus upload (decided 2026-10-31).** The conversion exists as separate command-line scripts in `scripts/`: `split_compiled_syllabi.py` (compiled PDF to course PDFs), `extract_syllabi.py` (PDF to JSON) and `resolve_review_syllabi.py` (repairs `needs_review` files). The extractor's template is documented as verified for text-native DLSU-D CICS PDFs only; behavior on other layouts is untested, and nothing connects an upload to these scripts or to `pre_model_data.py` yet.
  - An administrator uploads one single-course, text-native PDF. It is accepted when its text is extractable and `course_code` and `track` can be extracted. The title is metadata and not required. `needs_review` and issues carry through as warnings (§1).
  - After a new syllabus version is accepted, unchanged passages reuse their extraction by text hash; only the new version's passages are matched against the existing requirement groups; links to the replaced version are dropped; every aggregate is recomputed. This is valid because a component's support does not depend on other courses (§4).
  - A release is built in a temporary location and put in place only when its manifest is complete. On any failure the previous release stays active and a `failure.json` records the reason.
- **Pipeline entry point (interface approved 2026-10-31; not implemented).** One command takes the syllabus version, the job cutoff and a release id, and writes a release directory with its manifest. Exit status 0 is success, 1 a data failure, 2 an error; a failure also writes `failure.json`. The retrieval, support and grouping stages it calls are not built yet. The yearly start stays disabled until the standing source-access consent in collection plan §8 is recorded.
- **Unattended yearly collection** is decided (2026-10-30) inside a USD 5 per year cost ceiling; the standing source-access consent is still to be obtained by the user and recorded before any automatic run; see collection plan §8.
- **Classifier scope.** Which decisions it makes is undecided. Relevance and track are agreed. Cohort and Philippine eligibility may be simpler to read from work type and location fields.
- Each refresh still produces a new release with its own cutoff, syllabus version and rule version, so old results stay reproducible.

## 8. Result releases

Added 2026-10-31. A release is one immutable bundle of results written by a refresh; it is never edited, and a refresh writes a new one. Pool and cohort are keys of result sets inside the release, and each result set carries its own observation window, syllabus version, rule version and counts (§2.6). A pool with no data has no result set (§1). The release manifest records the release id, its creation date, the model and configuration used (including the model that wrote any stored AI rationale, §6) and the input versions. Whether a release is used for a controlled evaluation is not part of this contract.
