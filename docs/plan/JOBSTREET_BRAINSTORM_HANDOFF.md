## Fixed context for the discussion

- Collect jobs related to **BSCS Intelligent Systems, BSCS Game Development, BSIT Network Technology and BSIT Web Development**, including relevant common computing roles. Search terms are discovery routes, not proof of track or career membership. A clear title may link directly; generic or conflicting titles need duties checked. Keep original employer titles and relevant jobs without a justified curated-role match.
- Include **all seniority levels** in employment. Collect actual internship/OJT vacancies as a **separate cohort**. Do not use ESCO occupations as track labels or student-facing career names. Keep relevant Philippine jobs, including remote roles open to Philippine applicants.
- Preserve full raw posting text and provenance. The pipeline extracts required technical capabilities from duties and qualifications; jobs without usable technical text cannot support demand or coverage metrics. Keep returned rows, distinct IDs, relevant jobs and technically assessable jobs as different counts.
- Use recent postings first and extend only as needed, with a twelve-month maximum. One query-limited snapshot supports observed demand counts, not a trend or a national market estimate.
- The long-term 1,000/4,000 employment targets are planning goals. The **next step is a small, capped yield experiment**, not another bulk campaign. Reuse saved IDs and descriptions. Internships do not increase the employment target.
- The downstream results need distinct, relevant postings with usable technical text **across all four tracks**, including common roles. A pile of repeated rows, title-only records, or jobs confined to one track will not support the planned student career comparisons or faculty demand/coverage views. The curated student-facing role list is still an input to confirm; collection should not wait for it or manufacture one from search strings.

## How to ask questions

Ask **one decision at a time**, then wait for the answer. Each question should contain, in this order: **(1) the initial decision in the old plan, (2) what changed or is still unknown, (3) why the choice matters to the planned data-flow outputs, (4) two or three concrete options with a recommended low-overhead option and its trade-off, and (5) one direct question**. Explain terms such as *distinct*, *usable technical description* and *yield* when first used. Do not ask a bare yes/no question that hides the alternative.

Use actual job-posting examples **only if the user requests them**; explaining a choice does not require opening collected descriptions. Do not quote or rely on the recent unreliable model run. Distinguish confirmed user choices from proposed defaults and measured results. After each answer, briefly record the decision and move to the next unresolved question. If the user challenges a proposal, revise it before proceeding. Do not turn the session into implementation design for backend, frontend or the analytical model.

## Decisions to resolve

These are prompts for the next conversation, **not predetermined answers**. Start with question 1 and adapt later options to the user's answers.

1. **Pilot success measure.** Initial decision: optimize *entry/junior model-accepted employment*, which no longer matches the all-seniority contract. The pipeline needs new distinct, track-related postings whose technical requirements can be extracted; a new source ID alone may not provide that. **Recommend:** report a funnel of billed rows → new distinct IDs → likely relevant jobs → jobs with usable technical text, plus new usable jobs per billed row/dollar; report internships separately. Alternative: count only new IDs (cheaper to measure but overstates usable yield). For relevance estimates, use a small human-checked sample or a clearly provisional title/duties screen; do not use old or unvalidated model labels as truth. **Ask which measure should govern pilot expansion.**

2. **Query selection.** Initial decision: use all 34 role strings, plus possible junior/graduate variants. Overlapping strings may buy the same postings, and junior-only variants miss other seniority levels. The four tracks and shared computing work still need discovery. **Recommend:** first compare saved source-ID overlap by query, keep a small complementary set covering the four tracks and common roles, then test only variants with a plausible new-job benefit. Alternative: repeat all 34 (broader exploration, higher duplicate cost). A new role string is a search candidate, not a new student-facing career. Keep internship variants separately visible. **Ask how much query breadth the first small comparison should include.**

3. **Collection route.** Initial decision: use the existing JobStreet actor and consider another actor for pagination. Current route controls and deeper yield have not been proved by the old plan alone. The pipeline cannot benefit when larger requests just repeat the same prefix. **Recommend:** use the existing route only while a bounded test shows new usable IDs; assess an alternative only if its current contract, detail fields, price, source permission and actual later-page yield check out. Alternative: switch route immediately (more setup and unknown cost). Local deduplication prevents double-counting, **not provider charges**. **Ask what evidence would justify testing or switching routes.**

4. **First paid pilot size and stop rule.** Initial decision: the previous campaign targeted a much larger batch; it returned roughly 700 rows with substantial overlap. The goal now is to learn which method works before spending for volume. **Recommend:** set a small cross-track query/page or result cap, a campaign charge cap, a per-run cap and a maximum number of paid starts; stop a route when new usable-job yield stalls or description quality fails. Alternative: another large batch (faster volume, more duplicate-cost risk). Reconcile the old billing discrepancy and current provider terms before any new paid start. **Ask for concrete pilot caps only after the route/query choice is understood.**

5. **Date-window expansion.** Initial decision: recent first, with a maximum twelve-month lookback. That bound remains; how fast to widen is unanswered. The faculty demand views must show the actual observation window, and a single snapshot cannot support trends. **Recommend:** test recent results first, then widen only if the distinct usable-job gain and budget justify it. Alternative: request the full twelve months immediately (potentially more old repeats/cost). **Ask what evidence should trigger a wider window.**

6. **Raw handoff and counts.** Initial decision: the old collection plan had a large model-admission handoff built around seniority and ESCO. The new data flow assigns role/track relevance and technical assessability downstream. **Recommend:** preserve every raw payload, but hand off a small normalized index of stable source ID, selected version/full description, original title, dates, location/remote evidence, query/run provenance, duplicate links and missing-field flags. Report returned, distinct, relevant and assessable counts separately, with costs. Alternative: add another collection-side semantic classifier (more work and conflicting decisions). **Ask whether any additional field is needed for the agreed pipeline outputs.**
